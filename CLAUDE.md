# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A server-rendered blog/CMS built with Spring Boot 4.1.1 (Java 17), Thymeleaf, Spring Data JPA, Spring Security (form login), MySQL, and Flyway migrations. Frontend is plain jQuery (no SPA framework, no bundler) — DataTables.net for admin list tables (Users, Categories, Hashtags, Posts...), and a reusable `MediaExplorer` component (file-explorer UI driven by a JSON API) for the Media library and media pickers.

## Commands

Windows: use `mvnw.cmd`; Unix shells: use `./mvnw`.

- Run the app: `mvnw.cmd spring-boot:run`
- Build: `mvnw.cmd clean package`
- Run all tests: `mvnw.cmd test`
- Run a single test class: `mvnw.cmd test -Dtest=UserCrudTests`
- Run a single test method: `mvnw.cmd test -Dtest=UserCrudTests#testCreateUserSuccess`
- Run a nested test class: `mvnw.cmd test -Dtest=UserCrudTests$UserServiceUnitTests`

The app expects a MySQL instance reachable at `jdbc:mysql://localhost:3306/blog` with user `root` and empty password (see `src/main/resources/application.yaml`); Flyway auto-creates/migrates the schema on startup (`createDatabaseIfNotExist=true`), and `spring.jpa.hibernate.ddl-auto` is `validate` — schema changes must go through a new Flyway migration under `src/main/resources/db/migration` (currently up to `V25`), not entity annotation changes alone. Fake demo data (`V4` categories/hashtags, `V6` posts **and a demo admin `admin@kienhee.com` / `admin123`**) lives in `db/demo`, which only the default (dev) profile loads (`spring.flyway.locations`). `application-prod.yaml` (`SPRING_PROFILES_ACTIVE=prod`) uses `db/migration` only, turns on template caching, forwarded headers and both trash retention sweeps, and reads DB/mail settings from env vars. Never add demo `INSERT`s to `db/migration` (`DemoDataSeparationTests` fails).

## Architecture

**Layering**: `controller` (MVC, returns Thymeleaf view names or `redirect:` targets) → `service` interface + `service.impl` implementation → `repository` (Spring Data JPA) → `entity`. Request/response shapes for controllers are dedicated classes in `dto/`, validated with `jakarta.validation` annotations and bound via `@Valid @ModelAttribute` + `BindingResult` (not `@RequestBody`/JSON — this is a classic form-post MVC app). The one exception is the media module, whose explorer UI talks to a JSON API (`MediaApiController`, see Media library below); it still takes form params (not JSON bodies) and reuses the same DTOs through a `jakarta.validation.Validator`. Business-rule violations in the service layer (duplicate slug, self-deletion, category cycles, folder-in-use, etc.) are thrown as `IllegalArgumentException` and translated by the controller into field/global `BindingResult` errors, flash `successMessage`/`errorMessage` attributes, or (JSON API) a 422 `{ "message": ... }` — services never touch HTTP concerns.

**Two controller trees**:
- `controller/*.java` (`PublicController`, `AuthController`, `MediaFileController`) — public-facing pages, auth, and public file serving; map to `templates/public/**` and `templates/admin/authentication/**` (yes, auth pages live under `admin/` — that directory name means "private app", not "admin-role-only").
  - **Public site** (`PublicController` → `PublicBlogService`): renders only `PUBLISHED` posts and `visible` categories; routes are `/`, `/news`, `/article/{slug}`, `/categories`, `/category/{slug}`, `/author/{id}`, `/search?q=`, with a 1-based `?page=` sized by the `blog.posts_per_page` setting (bare `/article`, `/category`, `/author` redirect). `PublicSiteAdvice` (scoped to `PublicController`) adds `site` (all settings), `siteTitle`, `siteDescription`, `mainAuthorId` and `suggestedPosts` for the layout. Templates format through the `@publicView` bean (`PublicViewHelper`: `date`, `readMinutes`, `dek`, `safeHtml`) — post content is editor HTML and must go through `safeHtml` (Jsoup safelist), never raw. Thymeleaf 3.1 evaluates `th:utext` and URL attributes (`th:src`, `th:href`) in restricted mode — no `@bean` calls and no static access such as `#locale.ENGLISH` there — so compute helper results with `th:with` first (`th:with="body=${@publicView.safeHtml(post.content)}" th:utext="${body}"`).
- `controller/admin/*.java` — one controller per admin resource (`UserController`, `CategoryController`, `HashtagController`, `PostController`, `MediaController`, `MediaApiController`, `RoleController`, `CommentController`, `SettingController`, `ProfileController`, `DashboardController`), all under `/admin/**`, rendering `templates/admin/**`. `UserController`/`CategoryController`/`HashtagController` are fully implemented CRUD; `CommentController` moderates reader comments (see Comments below). `SettingController` is a generic key/value store (`site_settings`, V17): every form field named `settings[<key>]` is saved under `<key>` with no Java or migration change; read values with `SettingService.get/getInt`.

**Admin CRUD controller pattern** (`UserController`/`CategoryController`/`HashtagController` are the reference implementations): a single `GET` action lists all rows and seeds empty `*CreateRequest`/`*UpdateRequest` model attributes for the create/edit forms; `POST` create/edit actions re-render the same list view with `model.addAttribute("openOffcanvas", "create"|"edit")` on validation failure so the offcanvas form reopens with errors, and redirect to the list with a flash message on success/failure. `PostController` follows the same shape but uses a full page (`post-new.html`) instead of an offcanvas, shared between create and edit via a `postId` model attribute that's null only in create mode.

**Auth model**: Spring Security form login authenticates against `email`/`password` params (`SecurityConfig`), backed by `CustomUserDetailsService`. Public paths (static assets, public pages, `/auth/**`, `/media/**`) are listed explicitly in `SecurityConfig.PUBLIC_MATCHERS`; add new public routes there. The admin layout exposes the CSRF token as `<meta name="_csrf">` (and `_csrf_header`) for AJAX writes.

**Registration & account status** (`V25`, `users.status` = PENDING / ACTIVE / DISABLED): `/auth/register` is always open. `RegistrationPolicy.isFirstAccount()` (empty users table) makes that sign-up an ACTIVE Admin (`AuthServiceImpl.register` locks the admin role row first so two first-run sign-ups can't both win); every later sign-up gets the `user` role and PENDING, and active admins are emailed. Only ACTIVE accounts sign in: `CustomUserDetailsService` maps PENDING → disabled and DISABLED → locked, and `SecurityConfig`'s `DaoAuthenticationProvider` checks the password **before** those flags (a stranger can't learn an account is pending); the failure handler sends `?pending=true` / `?disabled=true`. Admins approve/disable/enable on the Users page (`POST /admin/users/{id}/status`, `users:edit`): never your own account, only admins (`roles:edit`) change an admin, and the last ACTIVE admin can't be disabled, demoted or deleted; approval emails the person. Accounts an admin creates are ACTIVE. Tests that need "first account" behaviour use `@MockitoBean RegistrationPolicy`.

**Dashboard**: `DashboardService` computes every number with JPQL on each visit (no caching, no fake values); cards/lists are gated by `perms` in the template. The sidebar has no counters.

**Sign-in throttling**: `LoginThrottleFilter` (added before `UsernamePasswordAuthenticationFilter` in `SecurityConfig`) refuses `POST /auth/login` once `LoginAttemptService` has 10 failures for the email or 30 for the IP in 10 minutes (redirect `?locked=true`, password not checked); the form-login success handler clears the email's count. In-memory, single instance.

**Admin accounts are protected**: only an actor with `roles:edit` (checked in `UserController`, passed to `UserService` as `actorIsAdmin`) may grant the Admin (system) role or edit/delete an account that has it, and the last admin can never lose the role or be deleted. Users and categories that still have posts can't be deleted (clear message instead of an FK error).

**Bulk delete** on Users/Categories/Hashtags/Posts: `POST .../bulk-delete` with `ids`, behind each resource's `:delete` permission; `BulkDelete.run` sends every id through the normal single delete and reports deleted/skipped rows with reasons. `datatable.js` posts the checked rows of all pages to the table's `data-bulk-delete-url` via `khDialog`. There is no Export CSV.

**Footer social links** come from Settings keys `social.x` and `social.youtube`; only `http(s)` URLs are rendered.

**Scheduled posts** (`V21`, `posts.scheduled_at`): status SCHEDULED requires a future "Publish on" time (flatpickr in the editor, `yyyy-MM-dd HH:mm`, server time zone shown; checked in `PostController`, re-checked in the service). `ScheduledPostPublisher` runs every `app.posts.publish-check-ms` (30 s) and calls `PostService.publishDuePosts`, one conditional UPDATE that sets PUBLISHED and `published_at = scheduled_at` — idempotent and safe on several instances. Any other status clears `scheduled_at`; scheduling a published post takes it off the public site until its time. Without `posts:publish` the status and time are kept. Test runs set `app.posts.auto-publish=false` (Surefire) so the job never races tests; call `publishDuePosts(now)` directly.

**Trash** (`V22`, `/admin/trash`): posts, categories, hashtags and comments are soft-deleted. Their entities carry `@SQLRestriction("deleted_at IS NULL")`, so every JPA query (admin, public site, dashboard) already skips trashed rows — never add a manual `deleted_at` filter to JPQL. Deleting anywhere in the admin calls the repository's native `moveToTrash`; `TrashService` (native SQL through `JdbcTemplate`) is the only code that lists, restores or purges. Rules that keep references valid: a category with any posts or subcategories (trashed ones included) can't be trashed or purged; a post can only be restored while its category is live, a comment while its post and parent are live; a comment is trashed and restored together with its replies; purging a post removes its comments and hashtag links (FK cascade). Slug/parent/author checks count trashed rows via native `countAll…` queries, because the unique columns still hold them. Each Trash tab and action needs that module's `:delete` permission. Users and roles are not soft-deleted (media, comments and reset tokens reference users). Media keeps its own trash (`/admin/media/trash`). Tests must clean trashed rows with SQL, not repositories.

**Feeds**: `FeedController` serves `/rss.xml` (20 newest published posts), `/sitemap.xml` (static pages, articles, visible categories, authors) and `/robots.txt` (keeps crawlers out of `/admin/`, `/auth/`). Absolute URLs come from the current request, so behind a proxy they rely on forwarded headers (prod profile). XML is built by hand — escape with `FeedController.esc`.

**Staff replies**: `POST /admin/comments/{id}/reply` (`comments:edit`) → `CommentService.replyAsStaff`: posted under the signed-in account, approved, one level deep, and approves the comment it answers (and its thread root).

**WebP** is decoded by the TwelveMonkeys `imageio-webp` plugin (read-only), so WebP uploads get dimensions and thumbnails; `WebpDimensions` remains a header-only fallback.

**Trash retention**: `TrashPurgeJob` (daily, `app.trash.*`, off unless `auto-purge-enabled`) calls `TrashService.purgeExpired(retentionDays)`; items that still can't be purged stay.

**Page views** (`V23`, `post_view_daily`): `PublicController.article` records one view per request when `ViewCountingPolicy.isCountable` (real browser GETs only — no bots/tools by User-Agent, no prefetch, no missing UA, no signed-in staff with `dashboard:view`). `PageViewService` upserts per post per day; no IPs, cookies or user ids are stored. The dashboard shows 30-day views vs the previous 30 days and the most read posts. Tests that GET articles without a User-Agent record nothing.

**Newsletter** (`V24`, self-hosted over `MailService`): `POST /subscribe` (home page form and `/subscribe`, honeypot, throttled per IP/address, same answer whether or not the address is known) → confirmation email (token hashed, 7 days) → `/subscribe/confirm`. Every issue carries the subscriber's own `/subscribe/unsubscribe?token=` link, which opens a page with a POST button (mail scanners can't unsubscribe anyone). Admin `/admin/subscribers` (`subscribers:view|send|delete`): counts, send an issue (plain text, blank lines = paragraphs, escaped in the email) to CONFIRMED subscribers after commit, past issues, remove a subscriber. Gmail SMTP caps sending at roughly 500 emails a day.

**Not done on purpose**: rate limits (login, uploads, comments, reset, newsletter) are in-memory per instance; share them (e.g. Bucket4j + Redis) before running more than one instance.

**Email & secrets**: `MailService` (async; renders `templates/mail/*.html` with Thymeleaf, absolute links only — no `@{}` in mail templates) sends through Gmail SMTP (`spring.mail.*`). Credentials are **never** in tracked files: `application.yaml` imports the git-ignored `config/secrets.yaml` (copy `config/secrets.example.yaml`) or reads `MAIL_USERNAME`/`MAIL_PASSWORD`/`MAIL_ENABLED`/`APP_BASE_URL`. `app.mail.enabled=false` only logs subject + masked recipient (never the body, which can carry single-use links). Maven Surefire forces `app.mail.enabled=false` for test runs; tests that exercise mail also `@MockitoBean MailService` — keep both, an IDE test run bypasses Surefire.

**Password reset**: `/auth/forgot` → `PasswordResetService.requestReset` emails a random 43-char token (only its SHA-256 is stored, `V19`), valid 30 minutes, single use; a new request or a completed reset invalidates older links. The page always answers with the same neutral message (no account enumeration), and requests are throttled quietly (3 per email, 10 per IP per 15 minutes). `/auth/reset?token=` sends `Referrer-Policy: no-referrer`. There is no other self-service way to change a forgotten password — do not reintroduce one.

**RBAC (permissions)** — real, enforced, and easy to break if you're not aware of it:
- A `User` has one `Role`; a `Role` has many `Permission`s. Permissions are a **fixed seeded catalog** of 35 rows (`V20__Permission_catalog_v2.sql`, plus `subscribers:view|send|delete` in `V24`), one per real function of each admin module — `dashboard:view`; `posts:view|create|edit|publish|delete`; `categories:*` and `hashtags:*` (view/create/edit/delete); `media:view|create|edit|delete|purge`; `comments:view|edit|delete` (edit = moderate); `users:*`; `roles:*`; `settings:view|edit` — the UI assigns them to roles, it never creates new ones.
- `CustomUserDetailsService` turns those into Spring authorities whose names *are* the permission codes, plus `ROLE_<SLUG>`. Enforcement is `@PreAuthorize("hasAuthority('posts:create')")` on controller methods (`@EnableMethodSecurity` is on in `SecurityConfig`). **New admin write endpoints must be annotated** — an unannotated POST inherits only the class-level `*:view` check, so anyone who can see the page can call it.
- Templates get a `perms` model attribute (`Set<String>` of authority codes) from `GlobalControllerAdvice` for hiding buttons: `th:if="${perms.contains('users:create')}"`. That is **presentation only** — never rely on it for security.
- The "Admin" role (slug `admin`, formerly Owner) is flagged `system_role`: its permissions can't be edited and it can't be deleted, so the instance can't lock itself out. `V12` backfilled pre-existing users to it for the same reason. The only other seeded role is `user` (contributor: dashboard, write/edit posts without publishing or deleting, read categories/hashtags/comments, browse and upload media) — `PermissionCatalogTests` pins both, and fails when a `@PreAuthorize`/`perms.contains` code has no seeded row or a row is checked nowhere. Publishing is enforced in `PostController` (without `posts:publish` new posts are drafts and existing posts keep their status), not just hidden in the editor.
- **Writing tests against admin endpoints**: a bare `.with(user("x@y.com"))` or `@WithMockUser(roles={"ADMIN"})` now gets **403**, because neither grants permission codes. Use `TestAuth.owner()` / `@WithOwner` from `src/test/java/com/kienhee/blog/support/`.
- `User.role` is LAZY and `open-in-view` is off — any query whose result is rendered in a template (or serialized to JSON outside the service transaction) must join-fetch what it touches (`findAllWithRole()`, `findByEmailWithRole()`, `MediaService.getAllMedia()`), otherwise it throws `LazyInitializationException`.

**Current user / template globals**: `GlobalControllerAdvice` injects `currentUser` (looked up fresh from `UserRepository` by the security principal's email on every request) and `currentUri` (context-relative request path, for nav highlighting) into every Thymeleaf model — available in templates without controllers passing them explicitly.

**Templates**: Thymeleaf with the layout-dialect (`nz.net.ultraq.thymeleaf`). `templates/layout/{public,admin}-master.html` are the two base layouts; `templates/fragments/{public,admin}/*.html` are shared includes (header/footer/sidebar/topbar/dialog); actual pages live under `templates/public/**` and `templates/admin/**` and decorate one of the master layouts. `spring.thymeleaf.cache` is `false` for dev — flip to `true` for prod-like runs. **Thymeleaf gotcha**: `@{...}` (link expression) can't be nested inside `${...}` (variable expression) — write conditional links as `${cond} ? @{...} : @{...}`, never `${cond ? @{...} : @{...}}` (the latter parses `@{...}` as invalid OGNL and throws a `TemplateInputException` at render time). Also, `th:attr`-style custom attributes (e.g. `th:data-folder="${expr}"`) are silently *omitted* from the rendered tag when `expr` evaluates to `""` — code reading that attribute client-side (jQuery `.data()`) sees `undefined`, not `""`. And jQuery `.data()` converts an all-digit value such as a folder named `1234` into a Number — read names with `.attr('data-name')`.

**Static assets**: `src/main/resources/static/scripts/{core,auth,user,category,hashtag,post,media,public}` for app JS (vanilla + jQuery, one folder per module, no npm/webpack pipeline — files are checked in directly), `static/scripts/lib` for vendored libraries (jQuery, jQuery Validate, DataTables.net, flatpickr, Lightbox2, Cropper.js), `static/styles` for CSS (`main.css` site-wide tokens/components, `admin.css` admin-panel-specific, `styles/lib` for vendored library CSS).

**`core/admin.js` vs `core/datatable.js`**: `admin.js` holds cross-page primitives used by every module — `khToast()`, `khDialog(what, formSelectorOrCallback, description)` (opens the shared delete-confirmation dialog; on confirm it submits the given form or runs the given callback; `description` is the per-action consequence text, defaulting to "This cannot be undone."), offcanvas open/close, slug auto-fill (`data-slug-source`), and generic client-side validation helpers. `datatable.js` initializes DataTables.net on every `table.dt` on the page (column filters, sorting) — used by Users/Categories/Hashtags/Posts list tables. The Media library does **not** use DataTables — see below. Modals/menus fade via opacity with `visibility` flipping **instantly** on open (see the fade block at the end of `admin.css`); a transitioned `visibility` leaves them unclickable for the first frame.

**Media library** (`MediaController`, `MediaApiController`, `MediaFileController`, `MediaService`/`MediaFolderService`/`MediaOptimizationService`, `MediaStorageLayout`) is the most involved module — worth understanding before touching it:
- **One UI component, used everywhere.** `static/scripts/media/media-explorer.js` defines `MediaExplorer.mount(element, { mode: 'manage' | 'pick', accept, multiple, initialFolder, onSelect, onCancel })`. It renders the whole explorer (folder sidebar, breadcrumb, grid, filters, selection bar, right-click menus, new-folder modal, rename popover, detail panel, uploads) from the JSON API, and scopes every DOM lookup to its own element (`[data-mx="..."]` hooks, no ids). `media.html` + `media.js` only mount it in `manage` mode; the post editor mounts the same component in `pick` mode (`accept: 'image'`) inside its cover-image modal. **Change the explorer in one place and both follow** — don't reintroduce page-specific explorer markup or a second picker.
- **Full-height layout**: the explorer fills the height it is given and scrolls inside (`.mx-scroll` for the grid, the folder list for the sidebar); the page never scrolls. On `/admin/media` this comes from `.content:has(> #media-library)` in `admin.css` (a fixed-height column: viewport minus the 64px topbar, with a 460px floor); it must keep `flex:0 0 auto`, because `.content` is `flex:1` in the layout and a flex-basis silently overrides `height`. The picker modal box is full viewport height (16px margin) and the explorer fills its body.
- **Pagination is client-side**: `/library` returns everything once and the component pages the filtered, sorted file list itself (pager below the grid; 12/24/48/96 per page, default 24, remembered per mode in `localStorage` under `kh.mediaExplorer.pageSize.<mode>`). Folders appear on page 1 only; filters, navigation, uploads and page-size changes go back to page 1; changing page deselects files that are no longer visible. Switch to server-side paging if the library grows into the thousands.
- **JSON API** (`MediaApiController`, `/admin/api/media`): `GET /library` returns folders, files, uploaders, trash summary and the caller's `create/edit/delete` permissions in one call (`?kind=image` for pickers); writes are form-param POSTs with CSRF (`/files`, `/files/{id}`, `/files/move`, `/files/{id}/delete`, `/files/delete`, `/folders`, `/folders/{id}/rename|move|delete`), each with its own `@PreAuthorize`. Errors are 422 `{message}`. Responses are rebuilt from `getAllMedia()`/`getFolderTree()` because they join-fetch what the JSON needs. The old redirecting form endpoints on `MediaController` still exist and are covered by tests; the trash page stays server-rendered with its own `/admin/media/api/trash/*` JSON endpoints.
- Accepts both images (JPG/PNG/WEBP/GIF/SVG) and documents (PDF/DOC(X)/XLS(X)/ZIP/TXT); validates content-type **and** magic bytes server-side through the `service/validation` chain (never trust the declared MIME type alone).
- **Storage mirrors the folder tree on disk**: files live under `app.upload.dir` (default `./uploads`) at `<ancestor folder slugs>/<sanitised original name>` (Windows-style ` (2)` suffix on case-insensitive clashes), thumbnails flat in `.thumbnails/`. They are served only through `MediaFileController` at the stable URL `/media/{id}/{filename}` (lookup by id; SVG/documents as attachments) — never under `static/`, and there is no `/uploads/**` handler. Renaming/moving a folder moves the directory and rewrites `media.storage_path` **and** `storage_blob.storage_key` for the whole subtree in one transaction; file writes go through `StorageTransactionHelper` so a DB rollback undoes them.
- Folders (`MediaFolder`) are **nested** via a materialized path (`path` like `/1/17/`, `depth`); moving a folder into its own subtree is refused.
- **Trash**: deleting a file or folder is a soft delete (`status = TRASHED`); deleting a folder trashes its whole subtree and files with one shared `deleted_at`, and restoring brings back exactly that batch. Only permanent delete (purge, needs `media:purge`) removes files and frees quota. Files used as a post cover or a user avatar cannot be deleted.
- **Image editor** (`static/scripts/media/image-editor.js` + `styles/image-editor.css`, on vendored Cropper.js): `MediaImageEditor.open(file, {canReplace, canCopy, onReplaced, onCopied})` does crop (ratio presets), rotate/straighten/flip/zoom, resize, brightness/contrast/saturation/grayscale/sepia and format/quality entirely on a canvas, then uploads the result. The explorer offers it (file menu + detail panel, manage mode only) for JPG/PNG/WEBP/GIF. "Replace original" → `POST /admin/api/media/files/{id}/image` (`media:edit`, `MediaService.replaceImage`): same id, URL, file name and **format** (a format change would change the URL that posts/avatars store); the old file is moved aside and deleted only after commit, the thumbnail is regenerated, and the owner's quota follows the new size. "Save as copy" → `/files/{id}/image-copy` (`media:create`) is a normal upload into the source's folder and may change format. Because edited files keep their URL, `MediaFileController` sends `Cache-Control: no-cache` plus an ETag derived from the file hash (304 on revalidation), and file JSON carries a `version` the explorer appends to preview URLs. **WebP**: the JDK's ImageIO cannot decode WebP (`ImageIO.read` returns null), so WebP width/height come from the RIFF header via `WebpDimensions` (VP8/VP8L/VP8X — Chrome's canvas encoder writes VP8X) on both upload and replace, and WebP files get no generated thumbnail (the file serves as its own). GIFs are exported by browsers as PNG, so a GIF can only be saved as a copy.
- **Preview** uses Lightbox2 (loaded globally by the admin layout): the zoom button on image tiles, "Preview" in the file menu (manage and pick mode), clicking the detail-panel image, or Space on a selection call `previewImage(file)`, which renders hidden `a[data-lightbox]` links for every image in the current filtered/sorted folder view (Lightbox2 only builds albums from links) and calls `lightbox.start`. Lightbox2 inserts captions as **HTML** unless `sanitizeTitle` is set — it is set globally in `core/datatable.js` and again in the explorer; keep it on, captions come from file names and post titles.
- Optimizes images through the TinyPNG API (`tinify.api-key`) **asynchronously** post-upload (`@EnableAsync` in `AsyncConfig`, actual call in `MediaOptimizationServiceImpl`) so the upload response isn't blocked on a third-party network call; falls back to the unoptimized original on any failure. A local (non-network) thumbnail is generated synchronously at upload time regardless of TinyPNG.
- Has its own in-memory `UploadRateLimiter` (sliding window per uploader) and a per-user storage quota (`QuotaService`).

**Comments** (`V18`, `Comment`/`CommentStatus`, `CommentService`, `PublicCommentController`, admin `CommentController`): readers post on `/article/{slug}/comments` (a public form post with CSRF). Guests give name + email (email is never rendered publicly) and start `PENDING` while the `comments.moderation` setting is on (default; checkbox on the Settings page); signed-in users are `APPROVED` immediately and named from their account. Replies are one level deep — a reply to a reply is stored under the top-level comment — and must target an approved comment on the same post. Spam defences: a hidden `website` honeypot (silently dropped), `CommentRateLimiter` (5 per IP per 10 minutes, in-memory) and CSRF. Comment text is rendered with `th:text` (escaped, `white-space:pre-line`), never `utext`. Admin moderation has per-row and bulk approve/unapprove/spam (`comments:edit`) and delete (`comments:delete`); bulk deletes use a JPQL `delete` and rely on the FK `ON DELETE CASCADE` for replies (deleting a post also removes its comments). The header's search overlay lists the newest posts on every public page, so public-page tests that assert a post is *absent* should check the model, not the whole HTML.

**Testing**: tests are `@SpringBootTest` + `MockMvc` (via `webAppContextSetup(...).apply(springSecurity())`), hitting a real (test) database rather than mocking the persistence layer — see `UserCrudTests` for the pattern of nested `@Nested` classes grouping DTO validation / service unit tests / controller MVC tests, using `TestAuth.owner(...)` and `.with(csrf())` for authenticated POSTs, and cleaning up any rows created during a test at the end of that test. Media tests (`MediaApiControllerTests`, `MediaCrudTests`, `MediaTrashTests`, ...) also remove the directories and files they create (`support/MediaFolderCleanup`). Mail is tested in `MailServiceImplTests` without Spring: a mocked `JavaMailSender` for the decision logic and an in-memory GreenMail SMTP server (`greenmail-junit5`, test scope) for the real MIME message — never point a test at a real SMTP account.
