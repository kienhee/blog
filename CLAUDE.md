# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

A server-rendered blog/CMS built with Spring Boot 4.1.1 (Java 17), Thymeleaf, Spring Data JPA, Spring Security (form login), MySQL, and Flyway migrations. Frontend is plain jQuery (no SPA framework, no bundler) — DataTables.net for admin list tables (Users, Categories, Hashtags, Posts...), and a reusable `MediaExplorer` component (file-explorer UI driven by a JSON API) for the Media library and media pickers.

## Commands

Windows: use `mvnw.cmd`; Unix shells: use `./mvnw`.

- Run the app: `mvnw.cmd spring-boot:run`
- Build: `mvnw.cmd clean package`
- Run all tests: `mvnw.cmd test`
- Run a single test class: `mvnw.cmd test -Dtest=UserCrudTests`
- Run a single test method: `mvnw.cmd test -Dtest=UserCrudTests#testCreateUserSuccess`
- Run a nested test class: `mvnw.cmd test -Dtest=UserCrudTests$UserServiceUnitTests`

The app expects a MySQL instance reachable at `jdbc:mysql://localhost:3306/blog` with user `root` and empty password (see `src/main/resources/application.yaml`); Flyway auto-creates/migrates the schema on startup (`createDatabaseIfNotExist=true`), and `spring.jpa.hibernate.ddl-auto` is `validate` — schema changes must go through a new Flyway migration under `src/main/resources/db/migration` (currently up to `V18`), not entity annotation changes alone. Migrations `V4` and `V6` seed fake demo data (categories/hashtags/posts) — safe for dev, not meant for a real production run.

## Architecture

**Layering**: `controller` (MVC, returns Thymeleaf view names or `redirect:` targets) → `service` interface + `service.impl` implementation → `repository` (Spring Data JPA) → `entity`. Request/response shapes for controllers are dedicated classes in `dto/`, validated with `jakarta.validation` annotations and bound via `@Valid @ModelAttribute` + `BindingResult` (not `@RequestBody`/JSON — this is a classic form-post MVC app). The one exception is the media module, whose explorer UI talks to a JSON API (`MediaApiController`, see Media library below); it still takes form params (not JSON bodies) and reuses the same DTOs through a `jakarta.validation.Validator`. Business-rule violations in the service layer (duplicate slug, self-deletion, category cycles, folder-in-use, etc.) are thrown as `IllegalArgumentException` and translated by the controller into field/global `BindingResult` errors, flash `successMessage`/`errorMessage` attributes, or (JSON API) a 422 `{ "message": ... }` — services never touch HTTP concerns.

**Two controller trees**:
- `controller/*.java` (`PublicController`, `AuthController`, `MediaFileController`) — public-facing pages, auth, and public file serving; map to `templates/public/**` and `templates/admin/authentication/**` (yes, auth pages live under `admin/` — that directory name means "private app", not "admin-role-only").
  - **Public site** (`PublicController` → `PublicBlogService`): renders only `PUBLISHED` posts and `visible` categories; routes are `/`, `/news`, `/article/{slug}`, `/categories`, `/category/{slug}`, `/author/{id}`, `/search?q=`, with a 1-based `?page=` sized by the `blog.posts_per_page` setting (bare `/article`, `/category`, `/author` redirect). `PublicSiteAdvice` (scoped to `PublicController`) adds `site` (all settings), `siteTitle`, `siteDescription`, `mainAuthorId` and `suggestedPosts` for the layout. Templates format through the `@publicView` bean (`PublicViewHelper`: `date`, `readMinutes`, `dek`, `safeHtml`) — post content is editor HTML and must go through `safeHtml` (Jsoup safelist), never raw. Thymeleaf 3.1 evaluates `th:utext` and URL attributes (`th:src`, `th:href`) in restricted mode — no `@bean` calls and no static access such as `#locale.ENGLISH` there — so compute helper results with `th:with` first (`th:with="body=${@publicView.safeHtml(post.content)}" th:utext="${body}"`).
- `controller/admin/*.java` — one controller per admin resource (`UserController`, `CategoryController`, `HashtagController`, `PostController`, `MediaController`, `MediaApiController`, `RoleController`, `CommentController`, `SettingController`, `ProfileController`, `DashboardController`), all under `/admin/**`, rendering `templates/admin/**`. `UserController`/`CategoryController`/`HashtagController` are fully implemented CRUD; `CommentController` moderates reader comments (see Comments below). `SettingController` is a generic key/value store (`site_settings`, V17): every form field named `settings[<key>]` is saved under `<key>` with no Java or migration change; read values with `SettingService.get/getInt`.

**Admin CRUD controller pattern** (`UserController`/`CategoryController`/`HashtagController` are the reference implementations): a single `GET` action lists all rows and seeds empty `*CreateRequest`/`*UpdateRequest` model attributes for the create/edit forms; `POST` create/edit actions re-render the same list view with `model.addAttribute("openOffcanvas", "create"|"edit")` on validation failure so the offcanvas form reopens with errors, and redirect to the list with a flash message on success/failure. `PostController` follows the same shape but uses a full page (`post-new.html`) instead of an offcanvas, shared between create and edit via a `postId` model attribute that's null only in create mode.

**Auth model**: Spring Security form login authenticates against `email`/`password` params (`SecurityConfig`), backed by `CustomUserDetailsService`. Public paths (static assets, public pages, `/auth/**`, `/media/**`) are listed explicitly in `SecurityConfig.PUBLIC_MATCHERS`; add new public routes there. The admin layout exposes the CSRF token as `<meta name="_csrf">` (and `_csrf_header`) for AJAX writes.

**RBAC (permissions)** — real, enforced, and easy to break if you're not aware of it:
- A `User` has one `Role`; a `Role` has many `Permission`s. Permissions are a **fixed seeded catalog** of 28 rows (`resource` × `action`, e.g. `posts:create`) — the UI assigns them to roles, it never creates new ones.
- `CustomUserDetailsService` turns those into Spring authorities whose names *are* the permission codes, plus `ROLE_<SLUG>`. Enforcement is `@PreAuthorize("hasAuthority('posts:create')")` on controller methods (`@EnableMethodSecurity` is on in `SecurityConfig`). **New admin write endpoints must be annotated** — an unannotated POST inherits only the class-level `*:view` check, so anyone who can see the page can call it.
- Templates get a `perms` model attribute (`Set<String>` of authority codes) from `GlobalControllerAdvice` for hiding buttons: `th:if="${perms.contains('users:create')}"`. That is **presentation only** — never rely on it for security.
- The "Owner" role is flagged `system_role`: its permissions can't be edited and it can't be deleted, so the instance can't lock itself out. `V12` backfills all pre-existing users to Owner for the same reason.
- **Writing tests against admin endpoints**: a bare `.with(user("x@y.com"))` or `@WithMockUser(roles={"ADMIN"})` now gets **403**, because neither grants permission codes. Use `TestAuth.owner()` / `@WithOwner` from `src/test/java/com/kienhee/blog/support/`.
- `User.role` is LAZY and `open-in-view` is off — any query whose result is rendered in a template (or serialized to JSON outside the service transaction) must join-fetch what it touches (`findAllWithRole()`, `findByEmailWithRole()`, `MediaService.getAllMedia()`), otherwise it throws `LazyInitializationException`.

**Current user / template globals**: `GlobalControllerAdvice` injects `currentUser` (looked up fresh from `UserRepository` by the security principal's email on every request) and `currentUri` (context-relative request path, for nav highlighting) into every Thymeleaf model — available in templates without controllers passing them explicitly.

**Templates**: Thymeleaf with the layout-dialect (`nz.net.ultraq.thymeleaf`). `templates/layout/{public,admin}-master.html` are the two base layouts; `templates/fragments/{public,admin}/*.html` are shared includes (header/footer/sidebar/topbar/dialog); actual pages live under `templates/public/**` and `templates/admin/**` and decorate one of the master layouts. `spring.thymeleaf.cache` is `false` for dev — flip to `true` for prod-like runs. **Thymeleaf gotcha**: `@{...}` (link expression) can't be nested inside `${...}` (variable expression) — write conditional links as `${cond} ? @{...} : @{...}`, never `${cond ? @{...} : @{...}}` (the latter parses `@{...}` as invalid OGNL and throws a `TemplateInputException` at render time). Also, `th:attr`-style custom attributes (e.g. `th:data-folder="${expr}"`) are silently *omitted* from the rendered tag when `expr` evaluates to `""` — code reading that attribute client-side (jQuery `.data()`) sees `undefined`, not `""`. And jQuery `.data()` converts an all-digit value such as a folder named `1234` into a Number — read names with `.attr('data-name')`.

**Static assets**: `src/main/resources/static/scripts/{core,auth,user,category,hashtag,post,media,public}` for app JS (vanilla + jQuery, one folder per module, no npm/webpack pipeline — files are checked in directly), `static/scripts/lib` for vendored libraries (jQuery, jQuery Validate, DataTables.net, flatpickr, Lightbox2), `static/styles` for CSS (`main.css` site-wide tokens/components, `admin.css` admin-panel-specific, `styles/lib` for vendored library CSS).

**`core/admin.js` vs `core/datatable.js`**: `admin.js` holds cross-page primitives used by every module — `khToast()`, `khDialog(what, formSelectorOrCallback, description)` (opens the shared delete-confirmation dialog; on confirm it submits the given form or runs the given callback; `description` is the per-action consequence text, defaulting to "This cannot be undone."), offcanvas open/close, slug auto-fill (`data-slug-source`), and generic client-side validation helpers. `datatable.js` initializes DataTables.net on every `table.dt` on the page (column filters, sorting) — used by Users/Categories/Hashtags/Posts list tables. The Media library does **not** use DataTables — see below. Modals/menus fade via opacity with `visibility` flipping **instantly** on open (see the fade block at the end of `admin.css`); a transitioned `visibility` leaves them unclickable for the first frame.

**Media library** (`MediaController`, `MediaApiController`, `MediaFileController`, `MediaService`/`MediaFolderService`/`MediaOptimizationService`, `MediaStorageLayout`) is the most involved module — worth understanding before touching it:
- **One UI component, used everywhere.** `static/scripts/media/media-explorer.js` defines `MediaExplorer.mount(element, { mode: 'manage' | 'pick', accept, multiple, initialFolder, onSelect, onCancel })`. It renders the whole explorer (folder sidebar, breadcrumb, grid, filters, selection bar, right-click menus, new-folder modal, rename popover, detail panel, uploads) from the JSON API, and scopes every DOM lookup to its own element (`[data-mx="..."]` hooks, no ids). `media.html` + `media.js` only mount it in `manage` mode; the post editor mounts the same component in `pick` mode (`accept: 'image'`) inside its cover-image modal. **Change the explorer in one place and both follow** — don't reintroduce page-specific explorer markup or a second picker.
- **Full-height layout**: the explorer fills the height it is given and scrolls inside (`.mx-scroll` for the grid, the folder list for the sidebar); the page never scrolls. On `/admin/media` this comes from `.content:has(> #media-library)` in `admin.css` (a fixed-height column: viewport minus the 64px topbar, with a 460px floor); it must keep `flex:0 0 auto`, because `.content` is `flex:1` in the layout and a flex-basis silently overrides `height`. The picker modal box is full viewport height (16px margin) and the explorer fills its body.
- **Pagination is client-side**: `/library` returns everything once and the component pages the filtered, sorted file list itself (pager below the grid; 12/24/48/96 per page, default 24, remembered per mode in `localStorage` under `kh.mediaExplorer.pageSize.<mode>`). Folders appear on page 1 only; filters, navigation, uploads and page-size changes go back to page 1; changing page deselects files that are no longer visible. Switch to server-side paging if the library grows into the thousands.
- **JSON API** (`MediaApiController`, `/admin/api/media`): `GET /library` returns folders, files, uploaders, trash summary and the caller's `create/edit/delete` permissions in one call (`?kind=image` for pickers); writes are form-param POSTs with CSRF (`/files`, `/files/{id}`, `/files/move`, `/files/{id}/delete`, `/files/delete`, `/folders`, `/folders/{id}/rename|move|delete`), each with its own `@PreAuthorize`. Errors are 422 `{message}`. Responses are rebuilt from `getAllMedia()`/`getFolderTree()` because they join-fetch what the JSON needs. The old redirecting form endpoints on `MediaController` still exist and are covered by tests; the trash page stays server-rendered with its own `/admin/media/api/trash/*` JSON endpoints.
- Accepts both images (JPG/PNG/WEBP/GIF/SVG) and documents (PDF/DOC(X)/XLS(X)/ZIP/TXT); validates content-type **and** magic bytes server-side through the `service/validation` chain (never trust the declared MIME type alone).
- **Storage mirrors the folder tree on disk**: files live under `app.upload.dir` (default `./uploads`) at `<ancestor folder slugs>/<sanitised original name>` (Windows-style ` (2)` suffix on case-insensitive clashes), thumbnails flat in `.thumbnails/`. They are served only through `MediaFileController` at the stable URL `/media/{id}/{filename}` (lookup by id; SVG/documents as attachments) — never under `static/`, and there is no `/uploads/**` handler. Renaming/moving a folder moves the directory and rewrites `media.storage_path` **and** `storage_blob.storage_key` for the whole subtree in one transaction; file writes go through `StorageTransactionHelper` so a DB rollback undoes them.
- Folders (`MediaFolder`) are **nested** via a materialized path (`path` like `/1/17/`, `depth`); moving a folder into its own subtree is refused.
- **Trash**: deleting a file or folder is a soft delete (`status = TRASHED`); deleting a folder trashes its whole subtree and files with one shared `deleted_at`, and restoring brings back exactly that batch. Only permanent delete (purge, needs `media:delete` + `settings:delete`) removes files and frees quota. Files used as a post cover or a user avatar cannot be deleted.
- Optimizes images through the TinyPNG API (`tinify.api-key`) **asynchronously** post-upload (`@EnableAsync` in `AsyncConfig`, actual call in `MediaOptimizationServiceImpl`) so the upload response isn't blocked on a third-party network call; falls back to the unoptimized original on any failure. A local (non-network) thumbnail is generated synchronously at upload time regardless of TinyPNG.
- Has its own in-memory `UploadRateLimiter` (sliding window per uploader) and a per-user storage quota (`QuotaService`).

**Comments** (`V18`, `Comment`/`CommentStatus`, `CommentService`, `PublicCommentController`, admin `CommentController`): readers post on `/article/{slug}/comments` (a public form post with CSRF). Guests give name + email (email is never rendered publicly) and start `PENDING` while the `comments.moderation` setting is on (default; checkbox on the Settings page); signed-in users are `APPROVED` immediately and named from their account. Replies are one level deep — a reply to a reply is stored under the top-level comment — and must target an approved comment on the same post. Spam defences: a hidden `website` honeypot (silently dropped), `CommentRateLimiter` (5 per IP per 10 minutes, in-memory) and CSRF. Comment text is rendered with `th:text` (escaped, `white-space:pre-line`), never `utext`. Admin moderation has per-row and bulk approve/unapprove/spam (`comments:edit`) and delete (`comments:delete`); bulk deletes use a JPQL `delete` and rely on the FK `ON DELETE CASCADE` for replies (deleting a post also removes its comments). The header's search overlay lists the newest posts on every public page, so public-page tests that assert a post is *absent* should check the model, not the whole HTML.

**Testing**: tests are `@SpringBootTest` + `MockMvc` (via `webAppContextSetup(...).apply(springSecurity())`), hitting a real (test) database rather than mocking the persistence layer — see `UserCrudTests` for the pattern of nested `@Nested` classes grouping DTO validation / service unit tests / controller MVC tests, using `TestAuth.owner(...)` and `.with(csrf())` for authenticated POSTs, and cleaning up any rows created during a test at the end of that test. Media tests (`MediaApiControllerTests`, `MediaCrudTests`, `MediaTrashTests`, ...) also remove the directories and files they create (`support/MediaFolderCleanup`).
